# ALPHA-TECH Recovery Workflow Consolidation

## Decision

Keep Workflow A as the mandatory recovery/backup authority and consolidate Workflow B (PostgreSQL Production -> Recovery/Standby clone) into the same scheduled execution.

The Windows Task Scheduler entrypoint is `scripts/run-recovery-task.bat`, which now invokes `recovery/consolidatedRecoveryRunner.js` only.

## Canonical flow

```text
Windows Task Scheduler
  -> scripts/run-recovery-task.bat
  -> recovery/consolidatedRecoveryRunner.js
       -> Workflow A (mandatory)
          recovery/jobRunner.js
          HEALTH_CHECK
          -> BACKUP
          -> VERIFY_BACKUP
          -> UPLOAD
          -> R2_RETENTION
          -> RETENTION
       -> Workflow B (optional; disabled by default)
          recovery/captureRecoveryBundle.js
          -> PostgreSQL read-only consistent snapshot
          -> public + legacy_tax bundle
          -> recovery/restoreRecoveryBundle.js
          -> Recovery/Standby DB
          -> row-count verification
```

## Authority rules

1. Workflow A always runs first. Workflow B must not run when Workflow A fails.
2. `recovery/jobRunner.js` remains the backup/verify/upload/retention authority. The consolidated runner calls it with `--no-standby-restore` so the legacy optional restore path cannot run in parallel with Workflow B.
3. Workflow B is not an independent scheduler. It is an optional stage of the same scheduled execution.
4. Workflow B is disabled unless `RECOVERY_STANDBY_SYNC_ENABLED=true`.
5. A standby sync additionally requires:
   - `RECOVERY_DRILL_APPROVAL=ALPHATECH_RECOVERY_DRILL`
   - `RESTORE_DATABASE_RESET_CONFIRMATION=ALPHATECH_TEST_DB_RESET`
   - `RESTORE_DATABASE_URL` or `RECOVERY_DATABASE_URL`
6. `restoreRecoveryBundle.js` retains `assertTestDatabaseAuthority(...)` as an independent target authority fence.
7. The source bundle capture is read-only and uses one PostgreSQL exported snapshot for row counts and `pg_dump`.
8. No scheduler should call `captureRecoveryBundle.js`, `restoreRecoveryBundle.js`, `qbrs.js`, or `qbv.js` directly.
9. Restore/reset is never enabled merely because the Windows scheduler runs. It always requires explicit environment approvals.

## Default scheduled behavior

The default behavior is intentionally unchanged in risk level. Without `RECOVERY_STANDBY_SYNC_ENABLED=true`, the scheduled task performs Workflow A only and records Workflow B as `SKIPPED`.

## Reports

The consolidated runner writes:

- `recovery/reports/consolidated-workflow-<run-id>.json`
- `recovery/reports/consolidated-workflow.latest.json`
- `recovery/logs/consolidated-<run-id>.log`

The existing Workflow A reports remain unchanged and are still generated by `recovery/jobRunner.js`.

## Rollout requirement

Do not enable standby sync on the scheduled task until local verification confirms:

- existing recovery safety contract PASS
- consolidation contract PASS
- recovery bundle contract PASS
- JavaScript syntax PASS
- one manual Workflow A-only run PASS
- one explicitly approved manual standby-sync drill against the authorized Recovery/Test target PASS

Production DB must remain source/read-only during standby capture. The only destructive reset target is the explicitly authorized Recovery/Test database.
